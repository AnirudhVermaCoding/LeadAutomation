# Security

What is enforced in code, what a basic penetration check covers, and what was found and fixed in the production-grade phase (2026-10).
Not a substitute for an independent penetration test before you take regulated data at scale.

## Enforced in code

| Area             | Control                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tenant isolation | Postgres row-level security on every tenant table; the app role is not a superuser and cannot bypass RLS; app code reaches tenant data only through `withTenant()`. A generated test (`rls-coverage.db.test.ts`) checks every table with a `tenant_id` column: RLS on + a policy, no rows visible without a tenant, each tenant sees exactly its own, another tenant's rows can't be updated or deleted. |
| Authentication   | Better Auth, email + password, no public sign-up, 12+ character passwords (also enforced when the agency creates a user), 7-day sessions, auth rate limits on in production. No email reset flow: the agency resets a password (`POST /v1/admin/users/reset-password`), which signs the user out everywhere. **No MFA yet** (roadmap).                                                                   |
| CSRF             | Cookie-authenticated writes under `/v1/` must come from our own origin (`Origin` / `Sec-Fetch-Site`); cookies are `SameSite=Lax`. API keys and webhooks carry no cookie and are unaffected.                                                                                                                                                                                                              |
| Rate limits      | 600 requests/min per IP overall (Meta webhooks and health checks exempt; loopback exempt outside production), stricter on the public lead form (10/min), `POST /v1/leads` (120/min) and the portal-email webhook (60/min).                                                                                                                                                                               |
| Webhooks in      | Meta: HMAC signature over the raw body on every call. Google: channel id looked up + channel token = HMAC of the id (constant-time compare). Portal email: a secret key in the path, rotatable.                                                                                                                                                                                                          |
| Webhooks out     | HMAC-signed with a timestamp; SSRF guard (public addresses only, checked on save and before every delivery; IPv4-mapped IPv6 handled; no redirects). Known gap: DNS rebinding between check and fetch.                                                                                                                                                                                                   |
| Secrets          | Per-tenant credentials AES-256-GCM, bound to tenant + name; key ring for rotation; opt-out hashes use a separate never-rotating key. Production refuses dev-only secrets and the dev database passwords.                                                                                                                                                                                                 |
| OAuth            | HMAC-signed `state` with expiry **and** a single-use nonce (a replayed callback does nothing). Scopes: `calendar.events` (+ `calendar.calendarlist.readonly`).                                                                                                                                                                                                                                           |
| Headers          | CSP (`default-src 'self'`, no framing; the hosted form has its own), `nosniff`, `X-Frame-Options`, referrer policy, Permissions-Policy, HSTS behind the proxy.                                                                                                                                                                                                                                           |
| Logs             | Ids only. Errors are scrubbed (SQL parameters, `Key (col)=(value)` details, emails, phone numbers); query strings of webhook / OAuth URLs dropped; `x-request-id` on every response. Tested with a real database error.                                                                                                                                                                                  |
| Data lifetime    | Retention per tenant (anonymize / delete), erasure, export; single-use OAuth states pruned daily, domain events after 180 days, AI call logs after 400 days.                                                                                                                                                                                                                                             |
| Dependencies     | `pnpm audit` is clean (an `esbuild` override removes a dev-only advisory) and runs in CI.                                                                                                                                                                                                                                                                                                                |

## Penetration checklist (run before each client go-live; results of the 2026-10-03 review in the last column)

| Check                                   | How                                                                                                                          | Result                                                                                        |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Cross-tenant read/write through the API | Sign in as clinic A, call every `/v1` route with clinic B's ids (leads, appointments, templates, links, blocked times)       | RLS returns 404/empty; generated DB-level test passes                                         |
| Forged webhook                          | POST `/webhooks/meta` with a bad / missing signature; POST `/webhooks/google-calendar` with a wrong token or unknown channel | 401 / 403 / 404                                                                               |
| CSRF                                    | Cookie + `Origin: https://evil` on a POST                                                                                    | 403                                                                                           |
| Replay the OAuth callback               | Reuse a used `state`                                                                                                         | Refused (single-use nonce)                                                                    |
| SSRF via outbound webhook URL           | Save `http://169.254.169.254/`, `https://[::ffff:a9fe:a9fe]/`, `https://localhost/`                                          | Refused (found and fixed: the guard's IPv6 / mapped-address regexes were missing backslashes) |
| Injection through customer text         | Prompt injection, "ignore your rules", fake tool results, HTML / SQL in names                                                | Guardrails (output guard, schema-validated tool calls); SQL is parameterised throughout       |
| Secrets in logs                         | Force a DB error containing a phone number; hit webhook URLs with tokens                                                     | Not logged                                                                                    |
| Brute force                             | 600+ requests/min; repeated bad logins                                                                                       | 429 (auth limiter on in production)                                                           |
| Session handling                        | Reset a password; reuse the old cookie                                                                                       | Signed out everywhere                                                                         |
| Backups                                 | Restore into a scratch DB; RLS intact; app role not super                                                                    | `deploy/restore-check.sh` (CI)                                                                |

## Found and fixed in this phase

- SSRF guard regexes missing backslashes (dead code), now tested with hex-mapped IPv4-in-IPv6 and `::`.
- Drizzle errors put bound SQL parameters (phone numbers, message text) in log lines and stored job output.
- Webhook and OAuth query strings (Meta verify token, Google `code`) were logged.
- No CSRF check on cookie sessions; no global rate limit; passwords of 8 characters accepted; admin-created users skipped the minimum.
- OAuth `state` could be replayed within its 10 minutes.
- An idle database connection error would crash the process; no handlers for unhandled rejections.
- `docker-compose` could start Postgres with the dev password in production.

## Known gaps (roadmap)

MFA / passkeys; password reset by email; DNS-rebinding window on outbound webhooks; an independent penetration test; Postgres WAL archiving (point-in-time recovery); dependency update automation (Dependabot) and image scanning in CI.
